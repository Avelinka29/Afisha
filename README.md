# ProfSkills — афиша студенческих мероприятий

Автор: **Максимчик Авелина**, МРК. Контакт: [avelina58100@gmail.com](mailto:avelina58100@gmail.com).

Приложение для студентов МРК: можно найти мероприятие, записаться на него и следить за объявлениями своих сообществ.

Сервер: PHP 8.2+ и MySQL 8+ (PDO MySQL, mbstring, fileinfo, session).
Composer и Node.js для серверной части не требуются.

## Структура работы по заданию

```text
конкурс/
├── module_a/     сервер, SQL-схема, заполнение БД и Postman-коллекция
├── module_b/     клиентское приложение
└── README.md     запуск и тестовые аккаунты
```

Модуль А — PHP API. Модуль Б — интерфейс на HTML, CSS и JavaScript без фреймворка. Готовая копия клиента находится в `module_b/dist`.

## Запуск на Mac

Все команды ниже выполняются из корня проекта.

1. Запустить MySQL. Если установлен через Homebrew: `brew services start mysql`.
2. Скопировать `module_a/.env.example` в `module_a/.env`, указать данные локальной БД. На текущем компьютере `.env` уже настроен. Файл исключён из Git.
3. Выполнить миграции и заполнить БД:

```sh
php module_a/bin/setup.php
```

Скрипт создаёт базу `profskills`, таблицы и тестовые записи. Уже существующие данные не стираются. Дополнительные мероприятия добавляются при повторном запуске без дубликатов. SQL-схема: `module_a/schema.sql`.

4. Запустить API:

```sh
php -S localhost:8000 -t module_a/public module_a/router.php
```

Проверка: <http://localhost:8000/api/health>. Ожидается `{"status":"ok","database":"connected"}`.

Для Windows с PHP в PATH используются те же команды. В Apache нужно направить document root в `module_a/public` и все API-запросы — в `index.php`.

## Запуск интерфейса

Оставить сервер API работающим. Во втором терминале из корня проекта выполнить:

```sh
php -S localhost:5173 -t module_b module_b/router.php
```

Открыть <http://localhost:5173>. Двойной клик по `index.html` не подходит: браузеру нужен HTTP-сервер для JavaScript-модулей и сессии.

Клиент работает без npm и Composer. Шрифты хранятся локально в `module_b/src/fonts`, лицензия — в соседнем `OFL.txt`. Для просмотра страниц достаточно локального API; реальная отправка почты требует интернета и SMTP-настроек.

Подготовить отдельную готовую копию клиента:

```sh
php module_b/build.php
```

Чтобы проверить именно эту копию, остановить второй сервер через Ctrl+C и запустить:

```sh
php -S localhost:5173 -t module_b/dist module_b/dist/router.php
```

Для напоминаний в третьем терминале:

```sh
php module_a/bin/scheduler.php
```

Он вызывает проверку напоминаний каждую минуту, пока терминал открыт. Вместо него можно настроить системный планировщик, как описано ниже. Запускать одновременно оба способа не требуется.

## Как устроен код

- `module_a/public/index.php` — точка входа: заголовки, сессия, общие проверки, вызов обработчиков.
- `module_a/src/bootstrap.php` — чтение `.env`, PDO, SQL-запросы, запись писем и уведомлений.
- `module_a/src/http.php` — JSON-ответы, валидация, пагинация, текущий пользователь и проверка прав.
- `module_a/src/auth.php` — регистрация, подтверждение email, вход, выход, пароли.
- `module_a/src/mailer.php` — отправка настоящих писем по SMTP с TLS.
- `module_a/src/events.php` — афиша, карточки, управление мероприятиями, записи, реакции, участники.
- `module_a/src/account.php` — профиль, списки кабинета, загрузка изображений.
- `module_a/src/admin.php` — верификация, блокировки, справочники и модерация.
- `module_a/schema.sql` — таблицы и ограничения базы.
- `module_a/bin/setup.php` — создание схемы и тестовых данных.
- `module_a/bin/reminders.php` — напоминания за 24 и 1 час.

Запрос проходит так: `index.php` → обработчик нужного раздела → проверка пользователя/данных → SQL → JSON. Все права проверяет сервер. Интерфейс только отправляет запросы и отображает результат.

Код удобнее читать с `public/index.php`, затем открыть нужный раздел, например `src/events.php`. Основные вспомогательные функции:

- `query()` — выполняет SQL с параметрами вместо подстановки пользовательского текста в запрос.
- `one()` — получает одну запись из базы или `null`, если ничего не найдено.
- `requireUser()` — проверяет, что пользователь вошёл, подтвердил почту и не заблокирован.
- `verified()` — проверяет права представителя именно в выбранном Комьюнити.
- `fail()` — останавливает обработку с кодом ошибки; `json()` — отправляет ответ.
- `transaction()` — сохраняет связанные изменения вместе или отменяет их при ошибке.

Например, при записи на событие сначала проверяются его статус, дата и свободные места. Затем сохраняются регистрация и уведомление. Эти действия идут в одной транзакции: если запись не удалась, уведомление тоже не останется в базе.

## Подключение интерфейса

Базовый адрес API: `http://localhost:8000/api`. Клиент разрабатывается на `http://localhost:5173`; другой адрес нужно указать в `CLIENT_URL` файла `.env`.

Используется сессионная cookie: JWT и `/api/auth/refresh` не нужны. Браузер должен отправлять cookie:

```js
const response = await fetch('http://localhost:8000/api/events', {
  credentials: 'include',
});
const result = await response.json();
```

Для POST/PATCH/PUT/DELETE с JSON добавить `Content-Type: application/json` и `body: JSON.stringify(data)`. После 401 открыть страницу входа. После успешного подтверждения email через GET сервер создаёт сессию и перенаправляет на `CLIENT_URL/`.

Использовать `localhost` и для API, и для клиента: не смешивать с `127.0.0.1` при работе с cookie.

Времена хранятся в UTC. `starts_at` и `ends_at` в карточках выдаются в ISO 8601 с `Z`. Для отправки времени из локальной формы использовать `new Date(value).toISOString()`, для показа — `toLocaleString()`. Остальные даты в ответах также относятся к UTC.

Обложки и аватары могут содержать путь `/uploads/...`: для изображения нужен адрес сервера, например `http://localhost:8000/uploads/cover-1.svg`.

## Формат API

Списки с пагинацией: `{"data":[],"meta":{"page":1,"per_page":12,"total":0}}`.
Карточки и профиль: `{"data":{...}}`. Справочники: `{"data":[...]}`.
Ошибки: `{"error":{"code":"EVENT_FULL","message":"Свободных мест нет"}}`.
Валидация: статус 422 и `error.fields` с массивами ошибок полей.

### Аутентификация

- `POST /api/auth/register` — name, email, password, faculty, course.
- `POST /api/auth/resend-verification` — email; повторное письмо для неподтверждённого аккаунта.
- `GET /api/auth/verify-email?token=...` — подтверждение, автовход и переход на клиент.
- `POST /api/auth/verify-email` — token; подтверждение и автовход с JSON-ответом.
- `POST /api/auth/login` — email, password; возвращает профиль и cookie.
- `POST /api/auth/logout` — уничтожение сессии.
- `POST /api/auth/password/forgot` — email; одинаковый ответ для известного и неизвестного адреса.
- `POST /api/auth/password/reset` — token, password; password_confirmation можно передать дополнительно.
- `POST /api/me/password` — current_password, password, password_confirmation.

Пароли хешируются через `password_hash`. Токены одноразовые, в базе хранится только SHA-256. Подтверждение действительно 24 часа, восстановление — час. Сброс пароля прекращает действие старых сессий.

### Афиша

- `GET /api/events` — category_id, club_id, format, date_from, date_to, upcoming, q, sort, page, per_page.
- `GET /api/events/{id}` — полная карточка и отметки текущего пользователя.
- `GET /api/clubs`, `GET /api/categories` — справочники.

`sort=starts_at|popularity`; популярность — активные регистрации + обе реакции. Общая афиша содержит только published. cancelled доступно по прямой ссылке; draft доступно только представителям своего Комьюнити.

`status`: draft/published/cancelled. `display_status`: planned/ongoing/completed для опубликованных событий. Карточка содержит registered_count, likes_count, interested_count, free_places, is_registered, my_reactions, can_manage. `capacity=null` означает отсутствие ограничения.

### Студент и кабинет

- `GET /api/me`, `PATCH /api/me` — профиль; менять можно name, faculty, course, avatar_url.
- `POST /api/events/{id}/register`, `DELETE /api/events/{id}/register` — записаться/отменить запись.
- `POST /api/events/{id}/reactions` — type: like или interested.
- `DELETE /api/events/{id}/reactions?type=like` — снять реакцию.
- `GET /api/me/registrations?period=upcoming|past` — регистрации с карточками. Без period — все.
- `GET /api/me/reactions` — реакции с карточками.
- `GET /api/me/notifications` — уведомления; ссылка на событие в payload.event_id.
- `PATCH /api/me/notifications/{id}/read` — отметить своё уведомление прочитанным.
- `POST /api/uploads` — multipart/form-data, поле file: JPEG, PNG, WebP до 4 МБ. Ответ data.url для обложки/аватара.

Повторная регистрация: 409 ALREADY_REGISTERED; мест нет: 409 EVENT_FULL; событие началось: 409 EVENT_STARTED; отменено: 409 EVENT_CANCELLED. После начала нельзя отменить свою запись. Проверка мест и запись выполняются в транзакции с блокировкой события.

Заблокированный пользователь получает 403 USER_BLOCKED на всех API, кроме GET /api/me при уже действующей сессии. Вход заблокированного также запрещён.

### Представитель

- `GET /api/me/events` — события всех Комьюнити, где пользователь верифицирован; фильтр status и общие фильтры афиши.
- `POST /api/events` — club_id, category_id, title, description, starts_at, ends_at, location, format, capacity (null или число), cover_url. Создаётся draft.
- `PATCH /api/events/{id}` — поля события, кроме club_id/created_by/status.
- `POST /api/events/{id}/publish` — публикация черновика.
- `POST /api/events/{id}/cancel` — reason; отмена с уведомлением участников.
- `DELETE /api/events/{id}` — удаление только черновика.
- `GET /api/events/{id}/participants` — участники с пагинацией.
- `GET /api/events/{id}/participants?export=txt` — текстовый экспорт UTF-8.

Верификация проверяется по связи пользователя с конкретным Комьюнити. При изменении времени/места создаётся event_changed, при отмене — event_cancelled, при записи — registration_confirmed, при заполнении последнего места — event_full автору события. При отмене записи сохраняются со статусом cancelled_by_organizer.

### Администратор

- `GET /api/admin/users` — пользователи с пагинацией.
- `PATCH /api/admin/users/{id}/block` — blocked: true/false.
- `PUT /api/admin/clubs/{clubId}/representatives/{userId}` — verified: true/false.
- `GET/POST /api/admin/clubs`, `GET/PATCH/DELETE /api/admin/clubs/{id}` — name, description.
- `GET/POST /api/admin/categories`, `GET/PATCH/DELETE /api/admin/categories/{id}` — name.
- `POST /api/admin/events/{id}/cancel` — reason; модерация.

## Письма и напоминания

Письма подтверждения и восстановления поддерживают настоящую отправку по SMTP и тестовую запись в файл. Настройки находятся только в `module_a/.env`, который исключён из Git. В `.env.example` секретов нет.

Для Gmail:

1. Включить двухэтапную аутентификацию Google и создать отдельный [пароль приложения](https://myaccount.google.com/apppasswords). Обычный пароль от Gmail для этой настройки не подходит. [Инструкция Google](https://support.google.com/accounts/answer/185833?hl=ru).
2. Заполнить локальный `module_a/.env`:

```dotenv
MAIL_TRANSPORT=smtp
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_ENCRYPTION=tls
SMTP_USERNAME=avelinka453@gmail.com
SMTP_PASSWORD=сюда_пароль_приложения
MAIL_FROM_ADDRESS=avelinka453@gmail.com
MAIL_FROM_NAME=Максимчик Авелина — На связи
```

3. Перезапустить API и зарегистрировать новый аккаунт. Письмо придёт на email, указанный при регистрации. Для ранее созданного неподтверждённого аккаунта на странице входа есть кнопка повторной отправки.

`MAIL_TRANSPORT=auto` использует SMTP, когда заполнен `SMTP_PASSWORD`, и тестовый режим, когда пароль отсутствует. `MAIL_TRANSPORT=log` принудительно включает тестовый режим. Пароль приложения сохранён только в локальном `.env`. Из текущей сети подключения к Gmail на портах 587 и 465 не установились; реальная доставка пока не подтверждена. После смены сети повторить проверку командой `php module_a/bin/test-mail.php`.

В тестовом режиме письма находятся в `module_a/storage/mail.log`, по одному JSON-объекту на строку. Скопировать полную ссылку из поля `text` и открыть в браузере. В режиме SMTP файл `mail-delivery.log` содержит только адрес, тему и факт отправки; токены туда не записываются. Журналы и сессии недоступны через веб-сервер.

При `MAIL_FALLBACK_LOG=true` ошибка SMTP переключает конкретное письмо в тестовый журнал, а интерфейс сообщает об этом. Так можно продолжать конкурсную проверку без доступа к почтовому серверу. При `MAIL_FALLBACK_LOG=false` ошибка SMTP отменяет регистрацию; клиент получает сообщение, а подробности находятся в журнале PHP.

Настройки Gmail основаны на [официальной документации SMTP](https://developers.google.com/workspace/gmail/imap/imap-smtp). Для другого провайдера нужно указать его SMTP-сервер и учётные данные.

Разовый запуск напоминаний:

```sh
php module_a/bin/reminders.php
```

На Mac/Linux добавить через `crontab -e` запуск раз в минуту, заменив пути на свои (путь к PHP узнать командой `which php`):

```cron
* * * * * /opt/homebrew/bin/php /absolute/path/to/project/module_a/bin/reminders.php >> /absolute/path/to/project/module_a/storage/reminders.log 2>&1
```

На Windows тот же скрипт запускается планировщиком заданий раз в минуту. Скрипт ищет события, до которых осталось 24 часа или 1 час с допуском 5 минут. Таблица reminder_deliveries не допускает дубликаты при повторных запусках. При переносе времени возможно новое напоминание.

## Проверка

Импортировать `module_a/profskills.postman_collection.json` в Postman. В начале каждой папки выполнить вход нужной ролью. Cookies сохраняются автоматически. Описание каждого запроса содержит условия использования. Запросы администратора и отмены действительно изменяют данные: выполнять осознанно.

Для автоматических проверок запустить отдельный API с тестовым режимом почты:

```sh
MAIL_TRANSPORT=log APP_URL=http://localhost:8001 php -S localhost:8001 -t module_a/public module_a/router.php
```

В другом терминале выполнить:

```sh
TEST_API_URL=http://localhost:8001/api python3 module_a/tests/smoke.py
```

Python нужен только для тестов; сервер полностью написан на PHP. Тесты проверяют HTTP-контракт и создают отдельный аккаунт и мероприятия. После проверки удалить только эти записи:

```sh
php module_a/tests/cleanup.php
```

Проверено 127 сценариев: права ролей, черновики, ограничения регистрации, реакции, уведомления, пароли, блокировки, справочники, загрузка изображений, экспорт участников и отсутствие повторных напоминаний.

Браузерные проверки находятся в `module_b/tests/browser.mjs` и `module_b/tests/forms.mjs` (для запуска нужны Node.js, Playwright и Google Chrome; для самого приложения они не нужны). Проверено 61 условие: создание и публикация, подтверждение почты с автовходом, восстановление/смена пароля, валидация, ошибка сети и отображение на ширинах 320/390/768/1440 px. Для тестов форм также используется `TEST_API_URL=http://localhost:8001/api`, чтобы не отправлять реальные письма на тестовые адреса. Снимки экранов сохраняются в `tmp/browser` и не входят в сдаваемый клиент.

Перечень требований и соответствующих страниц: `module_b/REQUIREMENTS.md`.

## Где показать базу данных

Используется **MySQL**, база **profskills**. Данные сохраняются после перезапуска сайта.

В PhpStorm: **View → Tool Windows → Database**, затем **+ → Data Source → MySQL**. Подключение: host `127.0.0.1`, port `3306`, user `root`, database `profskills`. Пароль взять из `DB_PASSWORD` локального `module_a/.env`. Нажать **Test Connection**, раскрыть базу и таблицы. Двойной клик по таблице открывает строки. При необходимости IDE предложит скачать драйвер MySQL.

Для демонстрации жюри открыть `module_a/database-demo.sql`: там готовые запросы для пользователей, верификации, событий, регистраций, реакций и уведомлений. Они только читают данные. Структура таблиц находится в `module_a/schema.sql`.

Через терминал (пароль вводится после запуска):

```sh
mysql -h 127.0.0.1 -P 3306 -u root -p profskills
```

Затем выполнить `SHOW TABLES;` или запросы из `database-demo.sql`.

## Как показать реакции, уведомления и верификацию

1. Войти как `student@example.com`, пароль `ProfSkills2026!`. В верхнем меню доступны **Мои реакции**, **Уведомления**, **Мои регистрации**. Эти разделы заполнены примерами. Новые реакции ставятся в карточке события; там же кнопка «Пойду».
2. Открыть **Кабинет → Мои сообщества и верификация**. У тестового студента Научное общество со статусом «Не верифицирован».
3. Выйти и войти как `admin@example.com`. Открыть **Верификация**, выбрать студента, Научное общество и «Выдать верификацию», затем «Сохранить».
4. Снова войти студентом. В профиле появится «Верифицирован», в меню — «Мои мероприятия». Теперь можно создавать события Научного общества; управление остальными Комьюнити остаётся недоступным.
5. Верификация Комьюнити выдаётся администратором. Подтверждение email — отдельная проверка через ссылку в письме.

## Поиск, ограничения регистрации и ответы API

Поиск находится над карточками на главной. Ввод и нажатие Enter или стрелки отправляют `GET /api/events?q=...`: поиск идёт по названию и описанию, вместе с выбранными фильтрами.

«Пойду» недоступна для отменённого, неопубликованного, начавшегося события и при отсутствии свободных мест. У уже зарегистрированного студента остаётся возможность отмены до начала, даже если все места заняты. При наступлении времени начала кнопка блокируется и на уже открытой странице.

Сервер проверяет те же правила независимо от интерфейса:

- `POST /api/events/3/register` — тестовое событие без мест, `409 EVENT_FULL`.
- `POST /api/events/4/register` — прошедшее событие, `409 EVENT_STARTED`.
- `DELETE /api/events/4/register` — отмена после начала, `409 EVENT_STARTED`.
- `POST /api/events/12/register` — отменённое событие, `409 EVENT_CANCELLED`.
- Повторная запись на то же событие — `409 ALREADY_REGISTERED`.

Эти запросы выполнять после входа студентом; иначе вернётся `401`. Пример ответа:

```json
{"error":{"code":"EVENT_FULL","message":"Свободных мест нет"}}
```

В Chrome открыть инструменты разработчика (на Mac `⌘⌥I`), вкладку **Network**, фильтр **Fetch/XHR**. Выполнить действие на сайте, выбрать запрос. В **Headers** виден HTTP-статус, в **Response** — JSON сервера, в **Payload** — отправленные поля. Поиск виден как запрос `events?q=...`. Заблокированная кнопка не отправляет запрос; для проверки серверного запрета использовать Postman-коллекцию в `module_a`.

## Вход через Google

На страницах входа и регистрации есть **«Продолжить с Google»**, в профиле — **«Привязать Google»**. Google подтверждает личность; сведения о курсе и специальности заполняются при первом входе. Также задаётся пароль для альтернативного входа по email. При последующих входах через Google пароль вводить не требуется.

Если профиль с таким email уже существует, сначала войти в него обычным способом и привязать Google в кабинете. Совпадение email не связывает аккаунты автоматически. Отказ пользователя и ошибки возвращают на страницу входа с понятным сообщением. Блокировка пользователя действует и для Google-входа.

Настройки OAuth находятся в локальном `module_a/.env`:

```dotenv
GOOGLE_CLIENT_ID=идентификатор_веб_приложения.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=секрет_веб_приложения
GOOGLE_REDIRECT_URI=http://localhost:8000/api/auth/google/callback
```

Client ID и Client Secret уже заполнены локально; секрет не включён в `.env.example`. В Google Cloud у OAuth-клиента типа **Web application** должен быть разрешён именно этот redirect URI. Если приложение находится в режиме Testing, аккаунт, которым выполняется вход, должен быть добавлен в Test users. Пароль приложения Gmail к этой настройке не относится.

Вход использует OAuth Authorization Code с PKCE, проверку state и nonce, RSA-подпись ID token, issuer, audience и срок действия. Для связи используется постоянный Google `sub`, а не изменяемый email. OAuth-токены не выдаются JavaScript-клиенту. Таблица `google_accounts` связывает Google с локальным пользователем; создаётся `php module_a/bin/setup.php`.

Проверки: `php module_a/tests/google.php` проверяет подпись и claims. `TEST_API_URL=http://localhost:8001/api python3 module_a/tests/google-http.py` проверяет завершение профиля и сессию; после него очистить тестовые данные обычным `cleanup.php`. Переход на настоящую страницу Google для приложения Afisha проверен; завершение входа под конкретным Google-аккаунтом требует действий его владельца.

[Документация Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server) · [Проверка OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).
